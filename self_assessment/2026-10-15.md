## Vedant

- **Work done this week:**
  - Confirmed the main dish against MariaDB's project page: vector search and RAG is **area 4**, and its
    stated criteria are a `VECTOR` column indexed over a real Wikipedia corpus queried with
    `VEC_DISTANCE_COSINE`, semantic search combined with ordinary SQL predicates in one statement, recall
    and latency measured against a ground-truth set we build ourselves, stated chunk/model/index parameters
    with reasoning, an ingest that runs from the README, and an explanation of what the database-native
    approach gives that a separate vector store would not.
  - Established that **the main dish needs its own repository.** The page requires one declared area on the
    first line of the README, and our existing repository declares area 2. Whichever area a README declares
    is the only one scored, so the two deliverables cannot share a repository.
  - **Probed MariaDB 12.3.3's vector support against a live local server** rather than working from
    documentation, and verified all three limitations Kaj Arnö named in the 17.09 session: a vector-indexed
    column must be `NOT NULL` (`ERROR 1252`), only one vector index is permitted per table (`ERROR 1235`),
    and the distance function must match the index. Also established a 16,383-dimension ceiling.
  - **Corrected one of those warnings.** Kaj said a mismatched distance function produces "meaningless"
    results. On 12.3.3 it does not: the optimizer silently declines to use the index and falls back to a
    full table scan with a filesort, so results stay correct and only performance collapses. A silent
    performance cliff, not silent corruption.
  - **Found a defect that is not in MariaDB's documentation.** A vector query filtered on a column that is
    not indexed on the vector-indexed table silently returns fewer rows than requested — no error, no
    warning. Asking for 10 rows where 20 satisfy the predicate returned between 0 and 7 across eight
    builds, and the count varies between rebuilds of the same index on the same data because HNSW assigns
    node levels randomly on insert. Filtering on an indexed column on the same table returned the correct
    count every single time. An initial run produced a tidy-looking non-monotonic table across
    `mhnsw_ef_search` which did not reproduce; the instability itself turned out to be the finding, and the
    write-up says so and marks the unstable numbers as not quotable.
  - Wrote the full specification for the main dish, `docs/main_dish_spec/` — 14 documents covering
    requirements traced to source, architecture, corpus design, chunking and the embedding-model decision,
    schema, retrieval and hybrid search, evaluation methodology, the RAG pipeline, risks, deliverables and
    open decisions, plus `probe/vector_probe.sql`, a runnable script that reproduces every verified claim.
  - Designed the schema around the measured behaviour: `category` is denormalised onto the chunk table and
    indexed, so the optimizer pre-filters and the result is both exact and complete.
  - Gated the defect behind a six-item verification checklist — reproduce at 384 dimensions on real
    embeddings, with genuinely random vectors, on 11.8 and the current release, on Linux, and search Jira
    for duplicates — before it goes in any public README or bug report.
